Read before touching `css/header.css`, `js/header.js`, `js/admin-bar-offset.js` or `js/mega-menu-offset.js`.

Digest of `README.md` §Extending and §Why you can't simplify this, which hold the full rationale and the measurements. Change one, change both.

- Contract = 2 classes and 1 property: `has-transparent-header` (user adds, on Template Part block), `is-scrolled` (plugin adds: opaque with page content under the header; on a solid sticky header, page has left the top), `--kntnt-header-visible-height` (plugin sets on root: window top the header covers, `0px` while slid away; read as `scroll-padding-top`).
- Transparent = **absence** of `is-scrolled`. Never an `is-transparent` class: a script-set class cannot exist at first paint → header flashes solid, then fades. Never invert.
- `js/header.js` owns the slide: `is-away` past the header's own height, back on an upward scroll of `JITTER` (4px), never while held (`[aria-expanded="true"]`, `dialog[open]`, `:focus-visible` in the group). `:focus-visible`, so a button clicked with the mouse holds nothing. `decideSlide` and `decideTransparency` are pure and tested: `composer test`, red before green. The DOM wiring is checked in a browser.
- Ollie Pro's script still runs and still sets `is-sticky-hidden`/`is-sticky-active`: it cannot be switched off without losing the toggle the plugin hangs on. So `:not(.is-away) { transform: none }` makes its classes inert (`none`, not `translateY(0)`: any transform makes the group the containing block of fixed descendants), `.is-away` carries the transform, and `z-index: 100 !important` beats the inline `-1` it writes once its own hide has finished. The 100 is copied from the theme's sticky rule.
- `is-scrolled` waits for the slide (`decideTransparency`), so the header never turns opaque just before sliding away. A timer says the slide has finished, never `transitionend`: no transition runs under reduced motion, and a resize can cancel one. The stylesheet's `transition-duration: 0s` is what the timer reads there.
- Transparent-mode rules are scoped to `header.has-transparent-header`. Everything else is not, **on purpose** – it serves sticky headers regardless of transparency, so scoping it to the class re-breaks solid headers. Never ‘tidy’ it under the class. `--sticky-full-offset` and the transition list key off `.wp-block-group[data-sticky-on-scroll-up="true"]`. The slide, the z-index, the shadow at the top, the panel's top, reduced motion and print key off that group directly inside `header`. The ≤600px `top: 0` reset targets `header:not(.has-transparent-header):has(> [data-sticky-on-scroll-up])` – every *solid* sticky header, excluding the transparent one (which is `fixed` and sets its own `top`).
- Transparent-state rule keeps its `!important` (core emits the block's own preset background as `.has-<slug>-background-color { background-color: … !important }` – nothing weaker beats it). An open menu changes nothing: the appearance follows the scroll position alone. Never put an `[aria-expanded]` clause back on it.
- Never write the `transition` shorthand on the header group. Ollie Pro sets `transition: transform …` at (0,2,0); a shorthand landing there resets it → header snaps, not slides. `transition-property` and `transition-duration` longhands only.
- Stylesheet must load after the theme's: enqueue priority 20, dep on the `ollie` handle. `position: fixed` ties Ollie's sticky rule at (0,2,2) – source order alone decides.
- The `@media (max-width: 600px) { … top: 0 }` rule fixes a **theme** specificity bug (in Ollie's `style.css`), not an Ollie Pro one. Ollie pins every sticky header down by the admin bar's height and ships its own ≤600px reset to `top: 0` – but that reset (specificity 0,1,1) is outweighed by its own unscoped base rule `body:not(.wp-admin) header:has(> .is-position-sticky)` (0,2,2), and media queries add no specificity, so the reset is dead code: the header rests 46px low once the now-`absolute` admin bar has scrolled out of view at ≤600px. Our rule restores the reset with a selector heavy enough to win (0,4,2). It stays pure CSS because a `sticky` header makes `top: 0` correct at both ends: in the flow at the very top it still tucks under the bar, and it sits flush once stuck. It excludes `.has-transparent-header` on purpose – those are `fixed`, not `sticky`, and a static `top: 0` would misbehave for them (empty band at 46px, or bar-overlap at 0px), so the transparent header's ≤600px gap is fixed separately (next bullet). Verified on `/partners/` at 400px, logged in.
- The transparent (`fixed`) header has the **same** ≤600px gap, but can't use the static `top: 0` reset: out of the flow, it would overlap the bar at the very top instead of tucking under it. So `js/admin-bar-offset.js` measures the admin bar's live bottom edge (`getBoundingClientRect().bottom`, clamped ≥0) into `--kntnt-admin-bar-offset`, and the `fixed` rule reads `top: var(--kntnt-admin-bar-offset, var(--wp-admin--admin-bar--height, 0px))` – so it tucks under the bar at the top and sits flush once the bar scrolls away. Reading scroll position is the one thing CSS can't do, which is why JS feeds it. The script is its **own file**, enqueued only when `is_admin_bar_showing()` (logged-in) and attaching its scroll listener only below 600px (`matchMedia`), clearing the variable above 600px so the fallback owns `top`. Don't merge it into `header.js`: that file's `is-scrolled` job runs for every visitor, so merging would ship admin-only code to everyone and into the cache-minified public bundle. The fallback keeps the static height before the script runs, with no JS, and for logged-out visitors (who have no bar to clear). Verified on the home page at 400px against a faithful admin-bar mock. Anchor positioning (`top: max(0px, anchor(--wpadminbar bottom, 0px))`) is the future pure-CSS replacement – switch once stable iOS Safari ships it.
- Requires *Hide in Scroll Down* (`data-sticky-on-scroll-up="true"`) on the group. Without it Ollie Pro's JS writes an inline `position` on the `<header>`, which beats the plugin's non-`!important` `fixed` rule → header never goes transparent. This is why the setup contract makes that toggle mandatory, and part of why the `fixed` rule can't just add `!important`.
- **Ollie Menu Designer mega menu:** `top: var(--kntnt-mega-menu-top, 100%) !important` on the panel, on every sticky header and at every width. Ollie sets the panel's `top` from its *Top spacing* as an **inline style via JS**, landing it ~25px inside the header's padding, and clears it on phones, where the panel then covers the header. `js/mega-menu-offset.js` measures the header group's live bottom edge minus the panel's offset-parent top into `--kntnt-mega-menu-top`; the rule hangs the panel from there. `!important` is unavoidable (beats Ollie's inline `top`); the custom-property indirection is deliberate – Ollie rewrites its inline `top` on resize but never touches the property, so the stylesheet keeps winning without a race. `100%` fallback hangs the panel from the nav item's own bottom before JS runs. The mobile overlay's `top: 0 !important` at (0,3,0) outranks this (0,2,1); keep it that way. The panel keeps Ollie's own fade: the header no longer fades when a panel opens, so there is nothing to sync.
- `js/mega-menu-offset.js` writes `--kntnt-mega-menu-top` on menu open (synchronously, before paint – no fallback flash) and on resize; skips the mobile overlay (`position: fixed`). Setting the top *before* the panel paints is the **handshake** with `kntnt-modal-mega-menu-ollie`: that plugin caps a tall menu's height ~100ms after open by measuring the panel's live top, so it reads the corrected edge with no shared event needed (the "guaranteed ordering" its `agents.d/modal.md` calls for). Loaded for every visitor (the panel opens for all), self-guarding on pages with no sticky header or no mega menu. Like the admin-bar offset, the whole thing is a **kludge replaceable by CSS anchor positioning** once Safari ships it – see `removable-workarounds.md`.
